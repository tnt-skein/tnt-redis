# Redis

`tnt-redis` — клиент Redis для Tarantool: RESP2 поверх встроенного
неблокирующего сокета. Соединения живут в пуле, срок один на вызов,
отказ — пара `nil, err` с родом по коду ошибки Redis, а команды
подряд уходят одной записью.

```lua
local redis = require('tnt.redis')

local client = redis.new({ host = 'cache', password = secret, pool = { size = 4 } })

local ok, err = client:command({ 'SET', 'user:7', 'Анна', 'EX', 60 })
local name, err = client:command({ 'GET', 'user:7' })   -- промах — nil без err
local replies, err = client:pipeline({ { 'INCR', 'hits' }, { 'EXPIRE', 'hits', 60 } })
```

Отказ — пара `nil, err`, где `err` — отказ `tnt-storage` с родом,
признаком отправки и приговором повтору. Исключение — ошибка
программиста: негодная команда или значение, незнакомая настройка.

Зависимости: [`tnt-must`](https://github.com/tnt-skein/tnt-must)
(проверки аргументов), [`tnt-log`](https://github.com/tnt-skein/tnt-log)
(журнал), [`tnt-pool`](https://github.com/tnt-skein/tnt-pool)
(соединения), [`tnt-retry`](https://github.com/tnt-skein/tnt-retry)
(повторы), [`tnt-external`](https://github.com/tnt-skein/tnt-external)
(подмена сети и шифрования в проверках),
[`tnt-storage`](https://github.com/tnt-skein/tnt-storage) (срок, отказ
с родом и запись значения строкой) и [`tnt-tls`](https://github.com/tnt-skein/tnt-tls)
(шифрование).

## Зачем пакет

Готового клиента Redis у Tarantool нет: ни модуля ядра, ни рока среди
официальных (`tt rocks search redis` пуст). Поэтому протокол свой — RESP2
поверх встроенного сокета, неблокирующего и живущего с файберами, —
а всё остальное взято готовым:

- пул — [`tnt-pool`](https://github.com/tnt-skein/tnt-pool/blob/main/docs/pool.md),
  который драйвер заводит сам, с проверкой живости без сети;
- отказ, срок и кодирование значений —
  [`tnt-storage`](https://github.com/tnt-skein/tnt-storage/blob/main/docs/storage.md):
  отказ `TntStorageFailure` с родом по первому слову ошибки Redis, один
  миг срока на вызов, диалект `redis` у `value.wire` — как записать
  строкой `int64`, время и точное число;
- повторы — [`tnt-retry`](https://github.com/tnt-skein/tnt-retry/blob/main/docs/retry.md)
  по полю `retriable` отказа;
- шифрование — [`tnt-tls`](https://github.com/tnt-skein/tnt-tls/blob/main/docs/tls.md).

RESP2 выбран, а не RESP3: вторую версию понимает всякий Redis и всякий
сервер, совместимый с ним, а третья дала бы словари и логику ценой
версии сервера не ниже шестой.

| Слой | Модуль | Что делает |
|---|---|---|
| протокол | `tnt.redis.resp` | команда в байты, запретные команды, разбор ответа циклом со стеком и пределом байтов — без сети |
| связь | `tnt.redis.link` | сокет и TLS, вход одним обменом, обмен в срок, живость без сети |
| настройки | `tnt.redis.settings` | умолчания, проверка, команды входа |
| драйвер | `tnt.redis` | пул, срок, повторы, отказ парой, возврат и выброс соединения |

Чего здесь нет:

- **Транзакций** — `MULTI`/`EXEC` исключение; атомарность даёт сценарий
  `EVAL`.
- **Подписок** (`SUBSCRIBE`, `MONITOR`): подписка занимает соединение
  целиком, а драйвер отдаёт его следующему после каждой команды.
- **Кластера и Sentinel** — драйвер ходит к одному узлу; `MOVED` и `ASK`
  приходят отказом `rejected`.
- **RESP3** — `HELLO 3` не шлётся; ответ RESP3 — отказ протокола.
- **Адреса строкой** (`redis://…`) и **сокета Unix** — только `host`
  и `port`.
- **Хранения значений Lua** — таблица уходит только явно,
  `storage.json(v)` либо `storage.binary(msgpack.encode(v))`: что и как
  класть, решает тот, кто кладёт, а не драйвер.

## Как пользоваться

Примеры в этом документе прогнаны на Redis 7.4 стенда (`make redis-up`,
`test/stand/redis.sh`); вывод — как напечатал прогон. Сертификаты
стенд кладёт в `/tmp/tnt-stand/tnt-stand-redis`.

### Драйвер: `redis.new`

```lua
local redis = require('tnt.redis')

local client = redis.new({
    host = '127.0.0.1',
    port = 16379,
    password = 'stand-secret',
    timeout = 2,               -- срок вызова по умолчанию
    pool = { size = 4 },
})

client:command({ 'SET', 'user:7', 'Анна', 'EX', 60 })
--> OK
client:command({ 'GET', 'user:7' })
--> Анна
client:command({ 'GET', 'user:8' })
--> nil
client:command({ 'MGET', 'user:7', 'user:8' })
--> { 'Анна', box.NULL }
client:pipeline({ { 'INCR', 'hits' }, { 'EXPIRE', 'hits', 60 }, { 'TTL', 'hits' } })
--> { 1, 1, 60 }
client:command({ 'LPUSH', 'user:7', 'x' })
--> nil, WRONGTYPE Operation against a key holding the wrong kind of value
--      (kind = rejected, sent = true, retriable = false, server_code = WRONGTYPE)

client:close()
--> true
```

Соединение открывается первым вызовом, а не в `redis.new`: драйвер заводят
при подъёме узла, когда ходить к чужой службе рано.

- `client:command(args, opts)` — одна команда. `args` — список: имя
  и аргументы. Ответ — значение Lua; промах (`GET` нет ключа) — `nil` без
  отказа, как у `box.space:get`; отказ — `nil, err`.
- `client:pipeline(commands, opts)` — команды подряд одним обменом:
  записаны разом, ответы — списком по порядку.
- `opts` у обоих — `{ timeout, idempotent }`: срок вызова и согласие
  на повтор после отправки (ниже, «Повторы»).
- `client:close()` — закрыть драйвер; `client:stats()` — показатели пула
  без учётных данных; `client.features.transaction` — `false`;
  `client.name` — имя драйвера.

### Цепочка: `pipeline`

Команды записываются одной записью, а ответы читаются по порядку — один
круг до сервера вместо стольких, сколько команд. Это не транзакция:
команды выполняются по одной, и чужие команды успевают между ними.
Ошибка любой команды — отказ всего вызова с её номером, хотя прочие
выполнены:

```lua
client:pipeline({ { 'SET', 'list', 'v' }, { 'LPUSH', 'list', 'x' }, { 'GET', 'list' } })
--> nil, команда 2 из 3: WRONGTYPE Operation against a key holding the wrong kind of value
client:command({ 'GET', 'list' })
--> v                       — первая команда выполнена
```

Пустой ответ внутри цепочки — `box.NULL`, а не `nil`: дыра в списке
сдвинула бы длину. Пустой список команд — исключение.

### Настройки

| Ключ | Что | По умолчанию |
|---|---|---|
| `host`, `port` | узел | `127.0.0.1`, `6379` |
| `username`, `password` | вход: `AUTH [username] password`; учётке ACL нужен пароль | без входа |
| `db` | номер базы: `SELECT` при входе | `0` |
| `tls` | `true` либо `{ verify, ca_file, ca_path, sni, cert_file, key_file }` для `tnt-tls` | открытый текст |
| `timeout`, `max_timeout` | срок вызова и его потолок, секунд | `5`, `60` |
| `max_bytes` | предел байтов на ответ (на все ответы цепочки) | 16 МБ |
| `pool` | `size`, `wait_timeout`, `idle_timeout`, `max_lifetime`, `open_cooldown`, `leak_timeout`, `sweep_interval` — как у `tnt-pool` | умолчания `tnt-pool` |
| `retry` | `attempts`, `base`, `factor`, `jitter`, `max` — как у `tnt-retry` | умолчания `tnt-retry` |
| `name` | имя в журнале, в пуле и в ведре повторов | `redis` |

Проверяется всё сразу в `redis.new`, и негодное — исключение на строке
того, кто завёл драйвер: опечатка `pasword` иначе молча оставила бы драйвер
без пароля. Срока и суждения о повторе в `retry` нет: срок у вызова свой,
а судит поле `retriable` отказа.

```lua
redis.new({ pasword = 'x' })
--> app.lua:1: настройки redis: ключа «pasword» нет, есть db, host, max_bytes,
--  max_timeout, name, password, pool, port, retry, timeout, tls, username
redis.new({ username = 'app' })
--> app.lua:1: настройки redis.username без password: вход по учётной записи ACL требует пароля
redis.new({ retry = { attempts = 0 } })
--> app.lua:1: настройки повторов: настройка attempts — целое число от 1, а пришло: 0
client:command({ 'GET', 'k' }, { timout = 1 })
--> app.lua:1: настройки вызова: ключа «timout» нет, есть idempotent, timeout
client:command({ 'GET', 'k' }, { timeout = 61 })
--> app.lua:1: timeout 61 с длиннее потолка max_timeout 60 с
```

### Команда и значения

Команда Redis — список строк байтов, и аргумент уходит строкой по правилу
диалекта `redis` из `tnt-storage` (`value.wire`):

| Аргумент | Уходит |
|---|---|
| строка | как есть, байт в байт: CRLF и нулевой байт внутри — часть значения |
| число | точной записью: целое — цифрами без степени, дробное — самой короткой записью, которая читается обратно тем же числом |
| `int64`, `uint64` | цифрами без `LL`/`ULL` |
| `decimal`, `uuid` | текстом |
| `datetime` | ISO 8601 со сдвигом числом: `2026-09-13T12:34:56.000000+0300` |
| `storage.json(v)` | текстом JSON |
| `storage.binary(s)`, `varbinary` | байтами |
| целое за ±2⁵³, NaN, бесконечность | исключение |
| `nil`, `box.NULL`, логика, таблица, функция | исключение |

Целое без степени — не вкус: `INCRBY k 1e+15` Redis отвергает
(«value is not an integer or out of range», проверено на 7.4), а `tostring`
в Tarantool пишет `1e15` именно так. Пустого и логики у Redis нет, и
угадывать за вызывающего, `''` это или `'0'`, драйвер не берётся.

```lua
client:command({ 'INCRBY', 'counter', 1e15 })          --> 1e+15 (число 1000000000000000)
client:command({ 'SET', 'price', decimal.new('1.10') }) --> OK; GET отдаёт '1.10'
client:command({ 'SET', 'doc', storage.json({ a = 1 }) }) --> OK; GET отдаёт '{"a":1}'
client:command({ 'SET', 'n', 9007199254740993LL })
client:command({ 'INCR', 'n' })                         --> 9007199254740994ULL
client:command({ 'SET', 'flag', true })
--> исключение: логику в Redis не передать: у него только строки — передайте строку явно
client:command({ 'SET', 'flag', box.NULL })
--> исключение: команда — массив, а не таблица с дырой на месте 3
client:command({ 'SET', 'flag', { 1 } })
--> исключение: значение table нельзя передать параметром: таблицу оберните json, байты — binary
```

`box.NULL` в команде отвергается раньше записи значения: в сравнении он
равен `nil`, и для проверки списка это дыра.

Ответ читается так:

| Ответ RESP2 | Lua |
|---|---|
| простая строка (`+OK`), строка байтов (`$…`) | строка |
| целое (`:…`) | число, пока оно не дальше ±2⁵³; дальше — `uint64` либо `int64`, как у msgpack самого Tarantool |
| массив (`*…`) | список; вложенность — как пришла |
| пустое (`$-1`, `*-1`) | на верхнем уровне `command` — `nil`; внутри массива и в ответах `pipeline` — `box.NULL` |
| ошибка (`-…`) | отказ всего вызова, даже если ошибка внутри массива |

Выборку драйвер к типам не приводит — число из `GET` остаётся строкой:
Redis хранит строки, а угадывать тип по значению значит портить строки,
похожие на числа.

Ответ дочитывается до конца и с ошибкой внутри: иначе недочитанный хвост
сдвинул бы следующему взявшему соединение все ответы на один. Разбор идёт
циклом со стеком, а не рекурсией, и ответ в сотню тысяч вложенных массивов
не роняет его «stack overflow».

### Отказ

Отказ — пара `nil, err`, где `err` — `TntStorageFailure`
([`tnt-storage`](https://github.com/tnt-skein/tnt-storage/blob/main/docs/storage.md),
«Отказ»): строкой, в JSON и в журнале — текст, а поля говорят, что делать.

| Где | Род | `sent` | `retriable` | Соединение |
|---|---|---|---|---|
| соединение не открылось, вход не уложился в срок, TLS не прошёл | `unreachable` | нет | да | не открыто |
| вход отвергнут: `WRONGPASS`, `NOAUTH`, `NOPERM`, `DENIED`, «DB index is out of range» | `denied` | нет | нет | закрыто |
| сертификат сервера не принят — `tnt-tls` назвал отказ словом `untrusted` | `denied` | нет | нет | закрыто |
| соединения из пула за срок не досталось | `busy` | нет | да | — |
| сервер занят и команду не выполнял: `BUSY`, `LOADING`, `MASTERDOWN`, `READONLY`, `TRYAGAIN`, `CLUSTERDOWN`, `NOREPLICAS` | `busy` | нет | да | в пул; после `READONLY` — выброшено |
| прав на команду нет: `NOPERM` | `denied` | нет | нет | в пул |
| прочая ошибка сервера: `WRONGTYPE`, `NOSCRIPT`, `ERR …` | `rejected` | да | нет | в пул |
| ответа нет за срок вызова | `timeout` | да | с `idempotent` | выброшено |
| связь оборвалась посреди ответа, ответ не по протоколу | `broken` | да | с `idempotent` | выброшено |
| команда не записалась целиком | `broken` | нет | да | выброшено |
| ответ длиннее `max_bytes` | `overflow` | да | нет | выброшено |
| драйвер закрыт | `closed` | нет | нет | — |

Род ошибки сервера решает её первое слово (`server_code`): так его и
пишет Redis — `WRONGTYPE`, `LOADING`. Общее `ERR` кодом не считается, и
род тогда решают слова отказа. Перечень кодов и слов — в `tnt-storage`
(`tnt.storage.codes`).

```lua
redis.new({ port = 16379, password = 'wrong' }):command({ 'GET', 'k' })
--> nil, redis 127.0.0.1:16379: вход не удался: WRONGPASS invalid username-password pair or user is disabled.
--      (kind = denied, sent = false, retriable = false, server_code = WRONGPASS)
redis.new({ port = 16379, username = 'reader', password = 'reader-secret' }):command({ 'SET', 'k', 'v' })
--> nil, NOPERM User reader has no permissions to run the 'set' command
--      (kind = denied, sent = false, retriable = false, server_code = NOPERM)
redis.new({ port = 1, timeout = 0.3, pool = { wait_timeout = 0.1 } }):command({ 'GET', 'k' })
--> nil, соединение не получено за 0.1 с: открыть соединение не удалось: redis 127.0.0.1:1:
--      соединение не открылось: Connection refused
--      (kind = unreachable, sent = false, retriable = true, server_code = nil)
client:command({ 'BLPOP', 'queue', 5 }, { timeout = 0.2 })
--> nil, redis 127.0.0.1:16379: ответа нет за срок вызова
--      (kind = timeout, sent = true, retriable = false, server_code = nil)
client:command({ 'EVAL', 'return {1, redis.error_reply("MY custom"), 3}', 0 })
--> nil, MY custom    (kind = rejected, sent = true, retriable = false, server_code = MY)
redis.new({ port = 16379, password = 'stand-secret', max_bytes = 1024 }):command({ 'GET', 'big' })
--> nil, redis 127.0.0.1:16379: ответ длиннее предела max_bytes: строка в 2000 байт, а осталось 1017
--      (kind = overflow, sent = true, retriable = false, server_code = nil)
client:close()
client:close()
--> false, redis: драйвер уже закрыт    (kind = closed)
client:command({ 'GET', 'user:7' })
--> nil, redis: драйвер закрыт    (kind = closed)
```

Исключение — только ошибка программиста: негодная команда или аргумент,
незнакомый ключ настроек, срок ноль, бесконечность или длиннее потолка,
а ещё команды, которые драйвер не отправляет (ниже).

В HTTP отказ сам не переходит: у него нет `status`, и код ответа выбирает
тот, кто отказ отдаёт наружу. Род подсказывает: `unreachable`, `busy`,
`timeout` и `broken` — служба недоступна сейчас, остальное — нет.

### Команды, которых драйвер не отправляет

Соединение живёт в пуле и после команды достаётся другому. Команда,
меняющая его состояние, отдала бы следующему взявшему чужую базу, чужую
учётную запись, начатую транзакцию или подписку, где ответы не отвечают
на команды. Поэтому это исключение до сети, а не отказ, — и в цепочке
тоже:

| Команды | Почему |
|---|---|
| `MULTI`, `EXEC`, `DISCARD`, `WATCH`, `UNWATCH` | транзакции нет (`features.transaction = false`): атомарность даёт сценарий `EVAL` |
| `SUBSCRIBE`, `PSUBSCRIBE`, `SSUBSCRIBE`, `UNSUBSCRIBE`, `PUNSUBSCRIBE`, `SUNSUBSCRIBE`, `MONITOR` | подписка занимает соединение целиком |
| `AUTH`, `HELLO`, `SELECT`, `RESET`, `QUIT`, `READONLY`, `READWRITE` | состояние соединения задают настройки драйвера |
| `SYNC`, `PSYNC`, `REPLCONF` | поток репликации — не ответ на команду |
| `CLIENT REPLY`, `CLIENT TRACKING` | меняют, на что отвечает соединение |

Имя сверяется без учёта регистра: `multi` — та же `MULTI`.

```lua
client:command({ 'MULTI' })
--> исключение: команду MULTI драйвер не отправит: транзакции у драйвера нет
--  (features.transaction = false): атомарность даёт сценарий EVAL
client:pipeline({ { 'GET', 'k' }, { 'SUBSCRIBE', 'news' } })
--> исключение: команду SUBSCRIBE драйвер не отправит: подписка занимает соединение целиком,
--  а драйвер отдаёт его следующему после каждой команды
```

### Срок

Один миг на вызов — `clock.monotonic() + timeout` на входе, — и перед
каждым ожиданием остаток считается заново от времени планировщика:
ожидание пула (не дольше `pool.wait_timeout`), вход, запись, ответ, пауза
повтора. Срок вызова — `opts.timeout`, иначе `timeout` драйвера.

Встроенный сокет срок принимает сам, поэтому работник в отдельном файбере
не нужен: чтение, не дождавшееся ответа, возвращает управление,
и соединение выбрасывается — в нём остался недочитанный ответ. Срок,
вышедший в ожидании пула, — `timeout` с `sent = false`, и соединение
возвращается: команда не ушла, сокет чист.

Блокирующая команда ждёт на сервере своего срока, и срок вызова обязан
быть длиннее его: иначе отказ `timeout` и выброшенное соединение.

```lua
client:command({ 'BLPOP', 'queue', 1 }, { timeout = 2 })
--> { 'queue', 'job' }
client:command({ 'BLPOP', 'queue', 0.1 }, { timeout = 2 })
--> nil                     — очередь пуста, сервер ответил пустым
```

### Повторы

Весь вызов идёт под `tnt-retry` со своим экземпляром на драйвер
(`scope` — имя драйвера), и повторяет он по полю `retriable` отказа:

- **до отправки — всегда**: соединение не открылось, пул занят, сервер
  ответил `LOADING` или `BUSY`, команда не записалась целиком;
- **после отправки — только с `idempotent = true`**: `timeout` и `broken`.
  `INCR`, оборванный после записи, сервер мог выполнить, и повтор посчитал
  бы дважды;
- **никогда**: `rejected`, `denied`, `overflow`, `closed`.

Из цепочки, записанной не целиком, первые команды могли уйти, поэтому
её повтор — тоже только с `idempotent = true`. Срок, вышедший до очередной
попытки, отдаёт отказ прошлой попытки без повтора: пауза `tnt-retry`
меряет свой срок от своего начала и может в него уложиться, не уложившись
в миг вызова. Повтор пишется в журнал `debug` самим `tnt-retry`.

### Соединения

- **Пул — `tnt-pool`**, заведённый драйвером; соединения открываются
  лениво. Одно соединение — одна команда за раз: RESP отвечает по порядку,
  и два файбера на одном сокете перепутали бы ответы.
- **Вход — один обмен**: `AUTH`, если задан пароль, `SELECT`, если база
  не нулевая, а без них — `PING`. Ответ на вход нужен всегда: сервер,
  у которого кончились места («max number of clients reached») или включён
  защищённый режим, отказывает на первую команду. `PING` рядом с `AUTH`
  был бы вреден: он в категории ACL `@connection`, и учётку только для
  чтения не пустил бы вовсе («NOPERM … 'ping'», проверено на 7.4).
- **Живость — без сети**: у открытого сокета — неблокирующий `sysread`
  одного байта. Свободному соединению сервер не шлёт ничего, и если читать
  есть что — конец потока после перезапуска сервера или `CLIENT KILL`, —
  соединение негодно, и пул открывает новое. Команда вызывающего при этом
  не теряется и не повторяется. Видно только то, что уже дошло до сокета
  клиента: закрытие, которое ещё в пути, когда команда уходит, обнаружит
  сама команда, а повтор решает раздел «Повторы»: записанную команду
  повторяет только `idempotent = true`.
- **`READONLY` — выброс соединения**: так отвечает бывший ведущий после
  смены, и новое соединение по тому же имени узла может прийти уже
  к новому ведущему.
- **Закрытие** закрывает пул: свободные соединения — сразу, занятые — когда
  их вернут. Повторное закрытие и вызов после — пара `closed`.
- **Отмена вызывающего** выбрасывает соединение и уходит дальше тем же
  исключением отмены, а не парой.

### Журнал

| Событие | Уровень | Поля | Кто пишет |
|---|---|---|---|
| соединение выброшено | `warn` | `driver`, `kind`, `reason` | драйвер |
| соединение не открылось | `warn` | `pool`, `err`, `streak` | `tnt-pool` |
| повтор | `debug` | `attempt`, `delay`, `err` | `tnt-retry` |

Ни команды, ни ключа, ни значения в журнале нет: в ключе бывает
опознаватель сеанса, в значении — что угодно. Текст отказа проходит
`scrub` из [`tnt-log`](https://github.com/tnt-skein/tnt-log/blob/main/docs/log.md).
Пароль уходит только в команду `AUTH` и нигде не показывается: ни
в `stats()`, ни в тексте отказа.

```lua
local sessions = redis.new({ port = 16379, password = 'stand-secret', name = 'sessions' })

sessions:command({ 'PING' })
sessions:stats()
--> { name = 'sessions', size = 8, busy = 0, idle = 1, total = 1, opened = 1, takes = 1,
--    gives = 1, drops = 0, discarded = 0, open_failures = 0, waiting = 0, waits = 0,
--    wait_timeouts = 0, leaks = 0, closed = false }
```

### Шифрование

`tls = true` — TLS с проверкой сертификата по системным корням;
таблица — настройки `tnt-tls`: `verify`, `ca_file`, `ca_path`, `sni`,
`cert_file` и `key_file`. Имя, по которому сверяется сертификат, —
`host`. Рукопожатие идёт в остаток срока входа.

```lua
local secured = redis.new({
    port = 16380,
    password = 'stand-secret',
    tls = { ca_file = '/tmp/tnt-stand/tnt-stand-redis/ca.pem' },
})

secured:command({ 'PING' })
--> PONG
```

Сертификат, который проверка не приняла, — `denied`, а не `unreachable`.
Корень стенда самоподписанный, среди системных корней его нет, и время
этого не лечит: пул отдаёт отказ сразу, вход пробуется один раз, и вызов
кончается за одно рукопожатие, а не в конце срока. Отказ узнаётся
по слову `untrusted`, которым его называет `tnt-tls`, а не по тексту:

```lua
redis.new({ port = 16380, password = 'stand-secret', tls = true }):command({ 'PING' })
--> nil, redis 127.0.0.1:16380: рукопожатие TLS не прошло: рукопожатие TLS не удалось:
--      сертификат не принят: self-signed certificate in certificate chain; …
--      (kind = denied, sent = false, retriable = false)
```

По умолчанию (`tls-auth-clients yes`) Redis требует от каждого клиента
сертификат, и его называют `cert_file` и `key_file` — файлы PEM, ключ
без пароля; ключ, лежащий в том же файле, что и сертификат, называть
не нужно. Ключ без сертификата — исключение в `redis.new`, а не отказ
при входе: это опечатка в коде, и видна она сразу.

```lua
local trusted = redis.new({
    port = 16381,
    password = 'stand-secret',
    tls = {
        ca_file = '/tmp/tnt-stand/tnt-stand-redis/ca.pem',
        cert_file = '/tmp/tnt-stand/tnt-stand-redis/client.pem',
        key_file = '/tmp/tnt-stand/tnt-stand-redis/client.key',
    },
})

trusted:command({ 'PING' })
--> PONG

redis.new({ tls = { key_file = 'client.key' } })
--> app.lua:1: настройки redis.tls.key_file без cert_file: ключ предъявляется только вместе с сертификатом
```

Без сертификата такой сервер не пускает. В TLS 1.3 рукопожатие
у клиента проходит раньше, чем сервер судит о его сертификате, и отказ
приходит на входе — `unreachable`, который пул повторяет до конца срока:

```lua
local _, err = redis.new({
    port = 16381,
    password = 'stand-secret',
    timeout = 1,
    tls = { ca_file = '/tmp/tnt-stand/tnt-stand-redis/ca.pem' },
}):command({ 'PING' })
--> err.kind == 'unreachable', текст кончается «вход не завершился: соединение
--  оборвалось: чтение из TLS не удалось: error:0A00045C:SSL routines::tlsv13
--  alert certificate required»
```

Соединение TLS, которое сервер закрыл в простое, пул видит до выдачи
так же, как открытое: живость спрашивается у `tnt-tls` (`link:idle`),
а он заглядывает в сокет, не вынимая из него ни байта.

### Подмена в проверках

Всё, чем пакет ходит в мир, объявлено внешними зависимостями
`tnt-external` в `tnt.redis.link` и подменяется в проверках по одной:
`connect` — открытие сокета, `secure` — рукопожатие TLS поверх открытого
сокета; его двойник отдаёт соединение с `read`, `write`, `close` и `idle`,
как у `tnt-tls`, а отказывает, как он, тройкой `nil, err, kind`, где
`kind` — `'untrusted'` либо пусто. Часы срока — у `tnt-storage`
(`storage.within._set_source`).
`_set_source(nil)` возвращает настоящие; незнакомое имя — исключение,
а не подмена мимо.

```lua
local link = require('tnt.redis.link')

link._set_source({
    connect = function()
        return nil, 'сети нет'
    end,
})
local _, err = redis.new({ timeout = 0.2 }):command({ 'PING' })
--> err.kind == 'unreachable', текст кончается «соединение не открылось: сети нет»
link._set_source(nil)
```

## Чем пришлось поступиться

- **Протокол свой.** Готового клиента нет, а блокирующая библиотека
  на C остановила бы весь узел. Цена — RESP2 и его проверка на нас.
- **Ошибка любой команды цепочки — отказ всего вызова**, хотя прочие
  команды выполнены. Кому важен ответ каждой, шлёт их по одной.
- **Ошибка внутри массива — отказ всего ответа**: остальные элементы
  теряются. Так отдают ошибку сценарии `EVAL`, и частичный ответ со
  спрятанной ошибкой хуже отказа.
- **Промах — `nil`, а пустое в массиве — `box.NULL`.** Два вида пустоты
  ради того, чтобы `if value then` работал на верхнем уровне, а длина
  массива не ломалась.
- **Живость без сети видит не всё.** У открытого сокета байты, пришедшие
  одним куском с ответом, уже лежат в буфере сокета, и проверка их
  не видит — сервер RESP2 таких не шлёт. Под TLS она строже, чем нужно:
  служебная запись, которую сервер вправе прислать и живому соединению
  (смена ключей), выбрасывает соединение — цена этого лишнее соединение,
  а не отказ на запросе, который уже ушёл.
- **Пока идёт сценарий-долгожитель, новое соединение не открыть**: сервер
  отвечает `BUSY` и на вход, и отказ выходит `unreachable`, а не `busy`.
  Оба повторяются, различие только в роде.
- **Непринятый сертификат сервера — `denied`, а наш, не принятый
  сервером, — `unreachable`**: первый `tnt-tls` называет словом
  `untrusted`, а второй приходит посреди входа отказом чтения, который
  от обрыва отличается только текстом OpenSSL, и вход повторяется до конца
  срока. `denied` здесь значит «вход не состоялся и время это не лечит»,
  хотя отказал не сервер, а проверка его сертификата.
- **Учётка без категории `@connection` и без пароля не войдёт**: вход без
  `AUTH` и `SELECT` — это `PING`. С паролем `PING` не шлётся вовсе.
- **Предел `max_bytes` — на весь ответ, и сверх него соединение
  выбрасывается**: дочитывать лишнее ради соединения — значит всё-таки
  принять то, от чего предел защищает.
- **Ключ клиента — только без пароля**: `tnt-tls` ключа под паролем
  не читает, и такой ключ — `unreachable` на входе до конца срока.

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`.

- `resp_test.lua` — протокол без сети: кодирование команды, запретные
  команды, каждый вид ответа, предел байтов, ответ в сотню тысяч вложенных
  массивов, беды протокола.
- `settings_test.lua`, `link_test.lua`, `redis_test.lua` — на двойнике
  сервера с настоящим сокетом на петле: вход, TLS через внешнюю
  зависимость, сроки, обрыв посреди ответа, соединение, закрытое
  в простое, отмена файбера, повторы по роду, срок на самой границе нуля,
  пул и закрытие.
- `redis_live_test.lua` — 13 проверок против Redis 7.4 в докере: значения
  туда и обратно, промахи, ошибки сервера с кодом, вход, ACL и `NOPERM`,
  база, срок, `CLIENT KILL` посреди вызова и в простое, `BUSY` от
  сценария-долгожителя, предел байтов, TLS с корнем стенда, `denied`
  сразу на сертификат неизвестного корня, сертификат клиента против
  сервера с `tls-auth-clients yes` и соединение TLS, убитое в простое. Стенд один на машину, а проверки идут разом из
  нескольких рабочих копий, поэтому каждая трогает только своё: ключи
  прогона, своё соединение в `CLIENT LIST`. `BUSY` занимает весь
  сервер, и для него у стенда свой сервер, на котором проверки встают
  в очередь ключом `SET NX PX`; сценарий-долгожитель кончается сам
  не позже чем через четыре секунды, и прогон, убитый посреди него,
  не оставляет сервер занятым.

```sh
make redis-up                                # Redis 7.4: порт 16379, TLS на 16380, TLS с сертификатом клиента на 16381, BUSY на 16382
.rocks/bin/luatest test/redis_live_test.lua
make redis-down
```

Без поднятого сервера живые проверки пропускаются: гейты не зависят
от докера. Без сети — 70 проверок за пять секунд; покрытие строк —
100 %, убитых мутантов — 100 %.
